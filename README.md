# 研织 ResearchMesh

**AI驱动的校园科研协作网络**

科研协作常常从一句不够清楚的话开始：“想做一个方向，但还不知道缺谁、怎么分工。”研织帮助学生和项目负责人把这样的想法整理成可以讨论的任务，再逐步完成找人、分工、合作约定与贡献记录。

AI负责理解和整理，人负责选择与确认。系统不会把一句兴趣描述当成能力证明，也不会替双方决定合作或公开个人经历。

## 从想法到一次有记录的合作

| 环节 | 研织提供的帮助 |
| --- | --- |
| 说出需求 | 从自然描述生成两个可选方向、建议任务与交付物，只追问影响下一步的关键问题 |
| 整理经历 | 从个人叙述提取做过的事，区分本人工作、团队成果、学习兴趣，以及独立或指导完成 |
| 寻找伙伴 | 按具体任务解释匹配依据，保留原文证据，指出缺口；条件尚不充分时提供低成本探索建议 |
| 商量分工 | 结合每周可投入时间比较组队方案，避免把几位排名靠前的人简单拼成团队 |
| 确认合作 | 整理任务、工时、交付和支持条件；条款修改后，双方重新确认同一版本 |
| 完成交付 | 辅助对照约定检查交付，由验收者作决定，再由贡献者核对本人记录与公开意愿 |

例如，一位同学想研究校园某类现象，却不知道如何组织工作。研织先把想法整理成可选择的方案；另一位同学只需描述自己的课程和项目经历，AI便据此提取与任务相关的线索。双方讨论后确定本周分工和交付标准，完成任务后再分别进行验收与贡献核对。这个过程不要求参与者一开始就会写专业需求书。

## AI如何参与

研织将自然语言理解用于需求梳理、经历抽取、逐任务匹配解释、合作条款整理和交付辅助分析。模型输出之后还有引用核对、条件检查和人工确认，避免将模型的推测直接写成事实。

“资料不足”“暂不适合”“需要指导”都是可以保留的结果。系统也支持退回、修改、拒绝、争议和超时，而不只展示一条顺利完成的路径。对初学者，已有经验与学习意愿分开表达，便于讨论有指导的参与方式。

## 当前进展

五个工作流已经搭建并发布，服务 API 已进行样例验证。本仓库收录五份 DSL 导出文件，合计 **100 个节点、121 条连线、11 个 DeepSeek 模型节点**，以及业务校验、接口适配和测试代码。节点数量描述的是流程规模，实际价值在于各环节能否衔接、证据是否可核对、双方能否保留决定权。

本地检查包含 96 项回归与权限测试，以及 9 项能力衔接断言。它们验证指定规则与样例，不代表已经完成真实校园试点或生产环境测试。

登录、数据库、跨用户权限、正式发布和用户主页网页仍需完成。当前工作流中的确认标记用于演示；个人贡献记录不构成技能认证，验收通过也不等于同意公开。

## 仓库内容

运行本地检查：

```bash
python3 scripts/run_contract_tests.py
```

参考代码测试使用 Python 3.12，无需调用模型。DSL 文件的解析和静态核对使用 PyYAML。

仓库不包含真实 API 密钥。部署时需在服务端配置自己的模型与 Dify 凭据。尚未指定开源许可证。
